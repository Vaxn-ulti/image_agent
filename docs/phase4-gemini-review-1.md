这是一份针对 `docs/phase4-plan-and-solve.md` 文件的产品可用性与 MVP 范围评审报告：

### 1. 方案亮点 (Strongest Parts)
*   **确定性清单 (Deterministic Inventory)**：在执行耗时的处理流程前，先返回确定的序列识别和转换报告。这种“先检查、再确认、后处理”的设计极大提升了临床/科研用户的掌控感和信任度。
*   **BIDS 标准化作为核心**：将杂乱的 DICOM/NIfTI 输入归一化为 BIDS 格式是行业标准做法，为后续扩展其他工具（BIDS Apps）打下了极佳的可扩展性基础。
*   **清晰的序列分类体系**：明确区分“支持处理”与“已识别但不提供处理”的序列，并提供统一的错误提示语。这种对用户预期的管理非常专业，避免了用户因尝试运行不支持的任务而产生的挫败感。
*   **灵活的部署模式**：支持 Local/Remote 两种模式，既照顾了个人研究者的本地便捷性，也预留了实验室服务器集群的扩展空间。

### 2. 具体风险与缺漏 (Concrete Risks/Gaps)
*   **大文件上传的超时风险**：API 设计中 `POST .../ingest` 提到支持“同步摘要”，但 1800+ 个 DICOM 文件的上传及 `dcm2niix` 转换可能耗时数分钟。在 Remote 模式下，浏览器或代理服务器极易发生 HTTP 超时。
*   **任务命名硬编码**：对于 BOLD 序列，方案默认任务名为 `rest`。对于做 Task fMRI 的用户，如果无法自定义任务名，会导致 BIDS 路径不符合其实际实验设计，影响后续分析。
*   **分类容错机制缺失**：序列识别高度依赖 Header 信息的准确性。如果算法将 T1 误判为 Unknown，用户在当前方案中似乎无法手动干预（纠正标签），这将导致数据无法进入后续处理。
*   **断点续传与部分重试**：如果 1000 个文件中只有 10 个转换失败（`completed_with_partial_failures`），方案未明确用户应如何只修复/补传这 10 个文件。

### 3. 必须修改的建议 (Must-change Suggestions)
*   **Ingest 接口异步化**：必须将 `POST .../ingest` 明确改为**完全异步模式**。返回 `task_id`，前端通过 `GET .../inventory` 轮询状态。避免同步等待导致的连接中断。
*   **增加序列标签手动校正**：在前端清单界面，应允许用户对识别出的序列标签进行手动修改（例如将 Unknown 修改为 T1），以应对自动分类算法失效的情况。这是保证 MVP 真实可用的“救命稻草”。
*   **明确 BOLD 任务命名输入**：在上传或清单确认阶段，允许用户输入 `task_name`（默认 `rest`），以符合 BIDS 规范对功能影像的要求。

### 4. 建议优化 (Optional Suggestions)
*   **集成轻量级 BIDS 校验**：在 BIDS 归一化完成后，调用一个简易的逻辑（或引用的 validator）确保生成的 `rawdata` 结构合法。
*   **进度反馈机制**：在 UI 上提供转换进度条（例如：正在转换第 5/10 个序列），而不是简单的“处理中”状态。
*   **重复上传检查**：在 `upload-session` 阶段，基于文件 Hash 或 DICOM StudyUID 做简单查重，避免浪费存储空间。

### 5. MVP 可执行性评价 (Implementable for MVP?)
**结论：是 (Yes)。**
该计划范围明确，成功锁定了最核心的“数据准入”痛点。虽然在接口同步性上存在风险，但逻辑框架非常完整。只要解决异步处理和手动校正标签的问题，该方案足以作为一个稳定、专业且可运行的 MVP 交付。
